# Alembic Migrations — BilimUz

## Why this exists

`database/schema/schema_v2.sql` was the fast way to get a full 54-table baseline during the architecture phase. But per `.cursor/rules/06-database-rules.md` ("Always create Alembic migrations. Never modify production database manually.") and `.cursor/prompts/02-database.md`, a raw SQL file with no version history and no rollback path is not acceptable once real environments (staging, production) exist. This directory closes that gap.

## Commands

```bash
cd backend

# Apply all migrations to the configured database (reads DATABASE_URL from .env via app.core.config)
alembic upgrade head

# Roll back the most recent migration
alembic downgrade -1

# See current DB revision
alembic current

# See full migration history
alembic history --verbose

# Create a new migration (once a module has a real models.py)
alembic revision --autogenerate -m "add roles module tables"
```

## Rules for this project specifically

1. **`0001_initial_schema.py` is a baseline migration, not autogenerated.** It wraps `schema_v2.sql` verbatim in `op.execute()`. This is a deliberate, documented exception to the 300-line file rule (it's 1126 lines) — see the file's own docstring. Never hand-edit it.

2. **`--autogenerate` is only safe once a module has a real `models.py` imported in `alembic/env.py`.** Today that's `auth`, `roles`, `subjects`, `users`. If you run `--autogenerate` before a module you're changing has models registered, Alembic will propose dropping every table it doesn't know about — **do not blindly accept an autogenerated migration**, always read the generated file before running `upgrade`.

3. **Every new module, when its `models.py` is written, must be added to the import list in `alembic/env.py`** (`from app.{module} import models as {module}_models  # noqa: F401`) — otherwise its tables silently stop being tracked.

4. **After `0001`, `schema_v2.sql` is historical only.** Schema changes happen through new migration files (`0002_*.py`, `0003_*.py`...), never by editing `schema_v2.sql` again.
